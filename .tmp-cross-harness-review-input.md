# Custodian Cross-Harness Modernization Handoff

**Status:** planning and source-verification checkpoint; no implementation sign-off yet.  
**Last consolidated:** 2026-08-05  
**Scope:** Custodian integration with Claude Code, Codex, Hermes/Talaria, OpenCode, direct shell/MCP paths, and the owner-only authorization boundary.

## 1. Executive decision

Build Custodian as a shared **policy-and-evidence plane**, not as five separate harness hooks. Native harness approvals remain the convenient interaction surface. Custodian evaluates and explains policy consistently; protected assets independently enforce owner-authorized capabilities.

This is intentionally phased:

1. **Observe:** consistent action records, gate receipts, logs, and cross-harness adapters.
2. **Audit UX:** owner-authorized, time-limited audit mode; every gate evaluates and reports, but does not itself block.
3. **Owner boundary:** policy and grant verification move outside agent-writable paths; only the operator can authorize relaxations.
4. **Asset enforcement:** high-impact resources validate Custodian capabilities independently of any harness.
5. **Assurance and adoption:** bypass testing, installer, managed configuration, documentation, and operator UX.

Do not claim harness-independent security before phases 3 and 4 are complete.

## 3. Non-negotiable requirements

### Default enforcement

- Enforcement remains fail-closed by default.
- A missing, invalid, or expired authorization returns to enforcement; no silent fallback to permissive behavior.
- No permanent removal of gates.

### Owner-authorized audit mode

- Every enabled gate evaluates on every relevant action.
- Each decision is visible and logged: gate identifier, enabled/audit state, matched facts, allow/deny verdict, reasoning, policy version, receipt ID, and correlation/action ID.
- A normal denial becomes `AUDIT WOULD-DENY` only under a valid owner grant.
- Audit mode must defer to the harness's native approval prompt; it must not blanket-allow a tool call and accidentally suppress native approval.
- A persistent status indication displays audit state, grant identity/scope, expiry, and would-deny count.

### Per-gate control

Each gate has a centrally governed state:

- `enforce`: evaluates and can block.
- `audit`: evaluates and logs but cannot itself block.
- `disabled`: only through an owner-signed, time-limited exception, with reason and receipt.

No environment variable, project configuration, user settings file, prompt, CLI flag, or agent-editable file is authoritative for relaxed modes.

### Anti-bypass principle

Codex, Claude Code, Hermes/Talaria, OpenCode, shell scripts, editor agents, MCP clients, and direct API callers running as `dev` are one untrusted **agent principal**. An agent must not gain authority by switching harnesses or asking another harness to act.

Only a separate owner authority may change policy, activate audit mode, disable a gate, approve a high-impact action, or deploy enforcement code. This requires a distinct principal—e.g. an admin-owned service plus a hardware-backed signing key requiring physical touch/PIN, or a separate admin device/account.

## 4. Architecture to build

```text
Harness UX
Claude | Codex | Hermes/Talaria | OpenCode | shell/MCP
          │
          ▼
Unprivileged Custodian adapters
canonical action → policy query → consistent receipt
          │
          ▼
Admin-owned Custodian authority
policy registry | append-only ledger | signed grants | verifier
          │
          ▼
Protected enforcement points
egress proxy | secret broker | VM/cloud/deploy APIs | privileged helpers
```

### Canonical action envelope

```json
{
  "action_id": "uuid",
  "principal": {"uid": 1000, "harness": "claude", "session": "..."},
  "workspace": {"path": "/repo", "repo_commit": "..."},
  "operation": {"kind": "exec", "target": "git push origin main"},
  "context": {"network": false, "credential_classes": [], "risk": "high"}
}
```

### Canonical decision response

```json
{
  "verdict": "allow | deny | require_owner | audit_would_deny",
  "native_prompt": "preserve | not_needed",
  "gates": [{"id": "network.egress", "enabled": true, "result": "deny", "reason": "..."}],
  "receipt_id": "cus_r_...",
  "capability_required": "cap_..."
}
```

### Capability/grant properties

Operator grants must be signed, short-lived, non-replayable, and bound to:

- owner authorization identity;
- requesting UID, harness, and session;
- workspace/repository and policy version;
- action class/target and optional object hash;
- individual gate exceptions;
- expiry and nonce.

Protected services validate the grant themselves. Hook output is an early UX control, not the sole security perimeter.

## 5. Harness adapter contract

| Harness/path | Required behavior |
| --- | --- |
| Claude Code | `PreToolUse` adapter records a decision; enforcement denies; audit reports `AUDIT WOULD-DENY` and pass-throughs to Claude native approval. |
| Codex | Adapter/wrapper provides the same receipt beside Codex sandbox and approval state. It must not confuse Codex approval with owner authorization. |
| Hermes/Talaria | Its approval callback consumes shared Custodian decisions; local manual/smart/off config is not authoritative for owner overrides. |
| OpenCode | Plugin/tool middleware issues the same policy query and renders the same receipt. |
| Direct shell/MCP/API | Sensitive resource/provider validates a Custodian capability, so bypassing a UI gains no power. |

## 6. What is recommended vs. rejected

### Recommended

- Keep native approvals for ordinary development interaction.
- Add verbose receipt logging and a clear persistent audit indicator.
- Start with source tracing and tests before editing hook behavior.
- Use injected signing/verification callables in code tests; test keys only.
- Use signed, expiry-bound grants for future audit/override operations.
- Run agents under a restricted agent identity/container for a real separation from the owner identity.

### Not recommended

- A global `CUSTODIAN_MODE=audit` environment variable as the final authority.
- An audit field in `~/.claude/settings.json` or project config that an agent can edit.
- Returning a blanket hook `allow` in audit mode if that bypasses native harness prompts.
- Relying on Claude `PreToolUse`, Codex approvals, or Hermes approvals alone as cross-harness security.
- Sharing an unlocked private signing key, cached sudo privilege, or generic privileged helper with an agent process.
- Moving immediately to root/system-wide mutation before the hook’s loaded source and behavior are proven.

## 8. Delivery phases and acceptance criteria

### Phase 0 — discovery and recovery

Deliverables: source-chain report, workspace-resolution diagnosis, test baseline, exact active configuration, and reversible immediate fix/documentation.

Pass criteria:

- imported hook path proven;
- behavior reproducible for root/home/project workspaces;
- no unrelated files staged or overwritten;
- fresh normal Claude session can perform normal project work;
- default fail-closed behavior retained.

### Phase 1 — common observability

Deliverables: canonical action/decision/receipt data model, gate registry, structured logs/ledger, test fixtures, and Claude adapter.

Pass criteria:

- every action produces a correlatable receipt;
- every evaluated gate reports enabled state, match, decision, and reason;
- no audit bypass exists yet;
- unit and integration tests cover canonicalization and logging.

### Phase 2 — audited development UX

Deliverables: owner-grant model (initially injectable test verifier), per-gate audit state, persistent status UI/output, native-prompt-preserving Claude behavior.

Pass criteria:

- enforcement still blocks without a valid grant;
- valid scoped audit grant produces would-deny receipts without Custodian blocking;
- native Claude approval is observed where normally required;
- tests cover expiry, wrong signer, tampering, replay, malformed grants, and per-gate scope.

### Phase 3 — cross-harness adapters and owner boundary

Deliverables: Codex, Hermes/Talaria, and OpenCode adapters; admin-owned policy/verifier deployment; hardware-backed or separate-admin signing workflow; signed updater.

Pass criteria:

- identical action semantics and receipt fields across harnesses;
- user/project/env changes cannot relax policy;
- agent cannot alter runtime, import path, or policy artifact;
- owner grant requires separate authority.

### Phase 4 — protected asset enforcement

Deliverables: capability validation in egress, secrets, cloud/VM/deploy, and privileged operation paths.

Pass criteria:

- direct shell, a second harness, and direct MCP/API calls cannot reach protected actions without a valid capability;
- grants are scope/expiry/nonce verified at every relevant enforcement point;
- negative bypass tests pass.

### Phase 5 — adoption and assurance

Deliverables: installer, managed configuration, migration guides, operator runbooks, receipt viewer, policy templates, performance tests, threat-model and penetration-test reports.

Pass criteria:

- easy local evaluation path;
- explicit managed/production deployment path;
- documented limitations and break-glass/revocation procedure;
- third-party/adversarial review completed.

## 9. Testing matrix

Required negative tests include:

- root, home-directory, unresolvable, and valid-repository workspace handling;
- malformed hook input and fail-closed behavior;
- each gate in enforce/audit/disabled states;
- missing, expired, tampered, wrong-key, wrong-workspace, wrong-harness, and replayed grants;
- changes to env, settings, PATH, PYTHONPATH, import location, symlink, and project config;
- attempts through Claude, Codex, Hermes/Talaria, OpenCode, shell, MCP, and direct provider API;
- ledger append/ordering/tamper detection;
- native approval remains visible during audit;
- no secret/private material appears in standard receipts/logs.

## 10. Required approvals and boundaries

### Already authorized direction

- repository-scoped discovery, design, implementation, and proportionate tests once the actual source checkout is proven;
- audit mode as an opt-in developer experience;

- use of an external signing device/key or production authorization grant;
