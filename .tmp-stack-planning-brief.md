## The architecture being planned (already decided, do not re-litigate)

Three orthogonal layers:
1. NVIDIA OpenShell — runtime isolation for the agent (Hermes runs inside its sandbox; MicroVM or strict driver, landlock hard_requirement).
2. iron-proxy (ironsh/iron-proxy) — network boundary: default-deny egress, dial-time CIDR deny (SSRF), proxy-token→real-secret swap at egress.
3. Paladin/custodian — authority layer: encrypted vault OUTSIDE the sandbox (per-run UDS in), harness guards (claude/codex/hermes hooks) governing every tool call, L0-L4 authority bands, approvals, oracle verification, tamper-evident receipts. Paladin issues the proxy tokens.

Secret flow: real secrets live only in Paladin's vault (at rest) and iron-proxy's secret source (swap). The agent holds only proxy tokens + scoped grants.

## Known facts to plan around (from a three-way security review, code-grounded)

- Paladin weaknesses the upper layers close: opt-in bwrap confinement; mask-list not allowlist FS exposure; egress hostname-only validation (DNS-rebinding gap); allowed_hosts=[] default; local-only audit.
- iron-proxy: not workload isolation (bypassable unless routing enforced); bearer tokens replayable; RFC1918 not denied by default; audit not tamper-evident.
- OpenShell: Landlock defaults to BestEffort (must set hard_requirement); empty policy = no restriction; isolation strength driver-dependent; policy complexity is a foot-gun.
- Paladin strengths: the only decision/authority layer of the three (L0-L4, approvals, oracle packs, receipts); the only Hermes integration (custodian-hermes-guard plugin).
- Custodian 0.5.0 is signed off and launch-ready; install matrix: pip | managed installer | hermes plugins enable.
